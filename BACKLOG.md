## Chores

- **Custom SMTP for Firebase Auth emails** — Firebase's sign-in link email template is non-editable (body is hardcoded, shows project ID "group-builder-backend" as app name). Custom domain (`noreply@group-builder.com`) and SPF/DKIM are already configured. To customize the email content: configure SMTP settings in Firebase Console → Authentication → Templates → SMTP settings to send through Resend. Then replace Firebase's `sendSignInLinkToEmail()` in `frontend/src/services/firebase.ts` with a backend endpoint that generates the sign-in link via Admin SDK (`generate_sign_in_with_email_link` — already used in `api/src/api/services/email_service.py` for invites) and sends a custom-branded email through Resend. Purely aesthetic — sign-in emails currently work and land in inbox. (2026-02)

- **Attribute focus switch** — Let the assignment view switch what the participant chips are *about*: religion (default), gender, or couples. One attribute at a time; per-table stats show all attributes regardless. Came from feedback that the colors are hard to read and icons might help. Part of the 2026-09 redesign. (2026-09)

- **Superlinear repeat penalty in the solver** — Repeats are currently penalized only within a rolling window (`pairing_window_size`, default 3), so a pair meeting in sessions 1, 4 and 5 is barely penalized and nothing counts total meetings per pair. Add a global per-pair repeat count with a superlinear penalty so a third meeting costs far more than a second. Chosen over a hard cap, which can make a program infeasible. (2026-09)

- **Extract the shared single-session re-solve** — `regenerate_single_session` and `regenerate_all_with_absences` in `api/src/api/routers/assignments.py` both do the same thing inline: take one session, gather the other sessions' pairings as history, re-solve that session alone with the absent participants removed, and merge the result back. The former is ~200 lines of handler around that core. Pulling it into one helper would shrink both and give the behavior a single place to be tested. Deliberately deferred out of the assignment-set rename branch because it is solver-adjacent and the rename must not change solver behavior. (2026-09)

- **Delete `api/src/api/storage.py` and its Upstash/Redis dependencies** — After the assignment-set rename, `storage.py` is a three-backend KV abstraction (Upstash/Redis/InMemory) plus a factory and a `REQUIRE_PERSISTENT_STORAGE` flag whose entire consumer surface is two lazy imports in `main.py:79,108`: one writes a `__health_check__` key and immediately deletes it, the other calls `close()`. All domain data lives in Firestore. The non-obvious part: `agent_docs/deployment.md:41` claims `UPSTASH_REDIS_REST_URL`/`_TOKEN` are for rate limiting — they are not. All three `Limiter(...)` constructions (`main.py:37`, `routers/assignments.py:18`, `routers/roster.py:19`) omit `storage_uri`, so slowapi uses in-process memory. Upstash is reached by nothing except `storage.py`, which is reached by nothing except a health check that pings Upstash — the loop closes on itself. Removable as a unit: `storage.py`, the `redis`/`upstash-redis` deps in `pyproject.toml`, the two deployment secrets (injected by both `deploy.sh` and `deploy-backend.yml`), and that deployment.md line. The health check reduces to `{"status": "healthy"}`. Diff is almost entirely red. (2026-09)

- **Delete the six permanently-skipped tests in `api/tests/test_rate_limiting.py`** — None can pass. Four assert 200 from assignment routes that now resolve an assignment set before reaching the mocked `handle_generate_assignments`, and no fixture creates one, so un-skipping yields 404 rather than a rate-limit signal. The other two (`TestUploadRateLimiting` at `:18,49`) POST to `/api/upload/`, and there is no upload router. Also worth recording: `client_with_rate_limiting` is, per its own docstring at `conftest.py:339-345`, just `TestClient(app)` "kept for documentation purposes" — the fixture named for the feature does not enable it. Six tests that read as coverage in the file listing while asserting things their fixtures cannot produce. (2026-09)

- **General keep-apart constraint** — Arbitrary pairs that must not share a table, alongside the existing linked-partners and couples-separation rules. Expect 0–1 pairs per program. Solver side should be close to existing couples separation; UI lives on the Setup page only. (2026-09)

- **Stable participant ids through the generate boundary** — Participants have no durable identity once assignments exist. Roster documents have stable Firestore ids and `partner_id` already references them, but `_roster_to_participant_list` (`api/src/api/routers/roster.py:55`) discards the doc id and writes `{"id": i + 1}` positionally, so everything downstream is name-keyed: the solver's seat dicts (`group_builder.py:671`) carry name and attributes but no id, absences match by name (`assignments.py:274`), and Item 7's version diff matches by name too. Consequence, already recorded as a known cost in the versions work: two people sharing a name collapse into one — in the diff, in the promotion count, and in absence records. The write path is cheap. The solver uses `p["id"]` only as a dict key and inside CP-SAT variable-name f-strings, both of which take strings, and its two internal name→id lookups (`group_builder.py:127,150`) exist only because seats lack ids — they get simpler. The expensive half is the read path: every stored version and every `participant_data` array predates the change, so consuming ids means a backfill or a permanent name-fallback matcher. Suggested shape if picked up: carry the real doc id at the generate boundary and emit it on seats *without reading it yet*, so documents written from then on carry identity and the later consumer migration needs no backfill — plus one test asserting the id survives generate, since an unread field rots silently. Considered during the 6a Roster lock design (2026-09-08) and deliberately deferred: nothing on the redesign board is blocked by it, and the duplicate-name failure is plausible rather than reported. Most likely to be forced by Item 4b (drag-and-drop wants stable keys) or the first duplicate-name bug. **Revisited for Item 6b (2026-09-10)** and again deferred: 6b lets a rename reach a *completed* session's frozen seating, and the call was to let it propagate there rather than refuse or special-case it (a coordinator renaming someone is almost always a correction; a delete+add that happens to look like a rename is the coordinator's own doing). So the name-match tax is now paid in frozen history too, not just the live roster — stable ids would erase that whole class of concern. (2026-09)

- **Delete the three orphaned whole-program solver endpoints** — after Item 6a moved the solve inside `POST /roster/generate`, nothing in `frontend/src` calls `GET /api/assignments/` (`assignments.py:367`), `POST /api/assignments/regenerate` (`:400`), or `POST /api/assignments/regenerate/with_absences` (`:439`). The first was the old second half of the two-call generate flow; the last was driven by the "Maintain saved absences" checkbox, which 6a deleted. `GET /` additionally had **no** completion guard while re-solving the whole program and saving a version — an orphaned route that could rewrite a completed Session's seating, against CLAUDE.md's "never modify a completed session". 6a added `refuse_if_any_session_complete` to it as a stopgap rather than deleting mid-branch. Deleting all three also retires `_generate_assignments_internal` and the direct `handle_generate_assignments` import in the router; `regenerate/session/{n}` (shuffle) stays and must keep working. Check `api/tests/test_rate_limiting.py`, whose four skipped assignment tests target these routes. (2026-09)

- **`solve_program`'s absence re-solve seeds history that never matches** — `program_solve.py` (~line 119) passes `extract_pairings_from_sessions(...)`, which yields *name*-keyed pairs, into `GroupBuilder(historical_pairings=...)`, which compares against *id*-keyed pairs. The repeat penalty for the re-solved session therefore never fires, so an absence re-solve can re-seat a pair that already met. PRE-EXISTING (not introduced by Item 6b; 6b's `solve_around_completed_sessions` correctly converts its own seed to ids). Same name-vs-id root as the stable-ids cluster below — fold the fix in there, or convert the seed to ids at the `solve_program` call site. (2026-09)

- **Rename side effects that stable participant ids would remove** — two known consequences of the Item 6a rename fast path, both rooted in name-matching and both cheap to live with until ids land (see the stable-ids entry above). (1) After an in-place rename, an *older assignment set's* `participant_data` still holds the old spelling, so `version_promotion.roster_change_reason` reports "1 person who has since left" for someone who only had their name corrected. (2) `POST /roster/discard` and the rename path each perform several Firestore writes without a batch: a crash mid-discard leaves the roster partially repopulated. Neither loses data — discard is idempotent and the page reads the truncated roster as dirty and offers Discard again — but a `WriteBatch` would close both. (2026-09)
